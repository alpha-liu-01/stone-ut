### Implementation notes

The sound card was already registered in item 2 (`holi-qrdsku1-snd-card`). There is no sound because PulseAudio cannot build a droid sink.

`module-droid-discover` loads `module-droid-card-30` from `ro.build.version.sdk` (34). That module does not recognize `AUDIO_OUTPUT_FLAG_SPATIALIZER` while parsing `/vendor/etc/audio/audio_policy_configuration.xml` (`immersive_out`, line 141). The whole policy is discarded, and only `sink.fake.sco` remains. After that port is removed, card-30 can parse the policy, but then it indirect-calls device vtable offset `0x110` inside `pa_droid_stream_set_route`. That slot is empty, and PulseAudio segfaults and exits. This HAL's `common.version` is `0x200` (`AUDIO_DEVICE_API_VERSION_2_0`). `open_output_stream` is at `0xd0`, not `0x110`. `module-droid-card-28` calls `0xd0`.

card-28's parser is older. It does not accept several flags, sample rates, or channel masks separated by spaces, and an included Bluetooth policy file trips an assertion that kills the process. The policy given to it was reduced in these ways: the spatializer port was removed, each flag, sample rate, and channel mask keeps only one value the parser knows, and the four included files were replaced with copies of the same reduction. `primary output` keeps `AUDIO_OUTPUT_FLAG_PRIMARY`.

The current session overrides `PULSE_SCRIPT` with phablet's user unit, pointing at `/home/phablet/.config/stone/touch.pa`, which was changed to load `module-droid-card-28`. That user configuration is still there after a reboot. The boot image does not have to be flashed again. The same change was placed in `boot/ut-init/rootfs-overlay/` (`/etc/pulse/stone-touch.pa`, the policies under `/usr/share/stone/`, and `pulseaudio.service.d/zz-stone-audio.conf`), so the next boot image carries it.

Result: both `sink.primary_output` and `sink.deep_buffer` exist, but the user confirmed neither the speaker nor the ringtone made any sound. `paplay` returning 0 only means the data entered the HAL. A 64-bit process loads `/vendor/lib64/hw/audio.primary.default.so` (an 11 KB empty AOSP implementation). The real HAL is the 32-bit `audio.primary.holi.so`, and PulseAudio cannot reach it.

Following `speaker` and `low-latency-playback` in `mixer_paths_qrdsku1.xml`, MultiMedia5 (`hw:holiqrdsku1sndc,9`) was connected to the speaker: `RX_MACRO RX2 MUX=AIF2_PB`, `RX INT2_1 MIX1 INP0=RX2`, `RX INT2_1 INTERP=RX INT2_1 MIX1`, `AUX_RDAC Switch=1`, `SpkrLeft Sipa Power=On`, `RX_CDC_DMA_RX_1 Audio Mixer MultiMedia5=1`. After a direct `aplay` to this device, the user confirmed they heard sound.

That path is now PulseAudio's default sink `sink.speaker` (`module-alsa-sink`). At boot, `speaker-route.sh` writes the mixer first. The current session uses the script and `touch.pa` in `/home/phablet/.config/stone/`, and they survive a reboot. The same files are `boot/ut-init/rootfs-overlay/usr/lib/stone/speaker-route.sh` and `etc/pulse/stone-touch.pa`, so the next boot image carries them. A 2-second 440 Hz tone was played again through `sink.speaker`, and the user confirmed they heard it. The earpiece and headphones are not on this path yet. The microphone and call audio are still undone.

The user then reported: the first key click after a pause is normal, and later ones are silent or very weak; ringtone preview in Settings does not play at all. The same operation plays the ringtone on Ubuntu Touch 24.04.2 on a Nothing Phone.

The unstable key clicks come from the mmap path in `msm-pcm-q6-v2.c`. At start it hands every period of the ring buffer to the DSP, and as soon as one finishes playing it queues it again. The DSP always holds the whole buffer. Data Pulse thinks it can still rewrite by rewinding has already been handed over. The first sound just after the device opens needs no rewind and is heard. While `module-suspend-on-idle` keeps the device open for about 5 seconds, later short sounds are inserted by rewind, so they are dropped or only a fragment remains.

The first change was `mmap=0`, and it was worse. In copy mode every write waits inside `msm_pcm_copy` for the DSP to return a period. Pulse's ALSA thread stays in D state for a long time, and the log says `q overrun, queuing locally`. The user heard a very large delay between key clicks, and the ringtone sounded about a minute later.

The current approach keeps mmap, shrinks the buffer to 4×10 ms (`fragments=4 fragment_size=1920`), and sets `rewind_safeguard=7680`, equal to the whole buffer. Pulse no longer rewinds, and a new sound starts at most 40 ms late. Six 80 ms tones in a row: each `paplay` took about 165 ms from connect to finished, with no queue. Both the user unit and the overlay `touch.pa` have been changed.

The ringtone does not play by writing to this sink directly. Preview in Settings is a Qt `Audio`, and Ubuntu Touch hands it to media-hub. This kernel's AppArmor does not fill in the peer label of a unix socket (`SO_PEERSEC` returns `ENOPROTOOPT`), and `/sys/kernel/security/apparmor/features/dbus/mask` does not exist. The session bus therefore answers `AppArmorSecurityContextUnknown` for every connection. media-hub gets an empty profile name and `abort`s, so the whole preview fails. The Nothing Phone's kernel can produce a label, so the same UI has sound.

The workaround lives in the user directory and does not need another boot image. `/home/phablet/.config/stone/media-hub-server` is a copy of `/usr/bin/media-hub-server`. An empty label is replaced with a static `unconfined` string, and parsing then continues as before. `~/.config/systemd/user/media-hub.service.d/zz-stone-unconfined.conf` points the service at that copy. `/usr/share/sounds/lomiri/ringtones/Ubuntu.ogg` was played along the same path Settings uses: media-hub no longer crashes, it plays on `sink.speaker` with `media.role=alert`, and it stops normally after about 8 seconds.

#### Why mobile data did not work, and the fix

It was not the APN, roaming, or the binder plugin. qcril's data module never initialized:

1. The vendor `netmgrd` (`ro.vendor.use_data_netmgrd=true`) waits after startup for `android.system.net.netd@1.1::INetd/default` (`V1_1::INetd::getService` plus `registerForNotifications`). The log stops at `NetmgrNetdClientInit(): Looking for Netd service`.
2. Halium runs no netd, and the Halium 14 system image has no netd stub. No netd service of any version exists on hwbinder or binder.
3. Until netmgrd is ready, DSI (`libdsi_netctrl`) cannot finish initializing. qcril initializes DSI only once, when it starts, so it never recovers. From then on, every `setupDataCall` gets `[CallManager]: DSI init not yet completed` inside qcril and is answered immediately with `respErr=4`, `cause=4100` (`OEM_DCFAILCAUSE_4`). It never reaches the modem. `imsd` gets stuck for the same reason (`dsi_get_data_srvc handle returned NULL`), so IMS cannot register either.
4. Side effect: `lomiri-indicator-network-service` retries immediately after every failure. That was over 10,000 times in one boot, and it stopped answering D-Bus, so Settings would not open and the Wi-Fi toggle did not take effect.

Fix: `stone-netd-stub.service` runs `usr/lib/stone/netd-stub.py` (python3-gbinder) and registers a stub INetd 1.1/1.0 on `/dev/hwbinder`. Every method returns a complete HIDL reply (transport status 0, then `StatusCode::OK`). `createOemNetwork` returns a handle of `(netId<<32)|0xfacade`. Routing and the firewall are still handled by NetworkManager. The stub has to register before qcril starts: `DefaultDependencies=no`, `After=lxc-android-config.service`, `Before=ofono.service`, `User=radio`. In practice it registers at 11.9 seconds, netmgrd calls `createOemNetwork` at 16.2 and 17.1 seconds (once per SIM), and qcril starts at about 15.3 seconds. Starting the stub after qcril is not enough (tested: netmgrd picked it up, but qcril stayed at `DSI init not yet completed`). Same idea as Halium/android_device_halium_halium_arm64 PR #39 and mer-hybris/dummy_netd.

Other configuration this depends on (in `boot/ut-init/rootfs-overlay/`):

- `etc/deviceinfo/devices/stone.yaml`: `OfonoPlugin: binder`, so `ofonod-wrapper` loads `ofono-binder-plugin` instead of the socket RIL plugin.
- `etc/ofono/binder.conf`: `ExpectSlots = slot1,slot2`. Each slot needs a `path` (`/ril_0`, `/ril_1`) and a unique `slot` (0, 1), or ofono silently drops the slot. Use `radioInterface = 1.5`, because the default 1.2 removes NR.
- `etc/ofono/binder.d/qti.conf`: `extPlugin = qti` (IMS registration, VoLTE calls, SMS over IMS).
- `etc/ofono/ril_subscription.d/stone.conf`: slots for `audiosystem-passthrough-qti` only.
- APN: ofono's apndb plugin does not match `mvno_type=gid` and picked Vidéotron's `media.ng` for this Fizz SIM. The internet context `/ril_0/context1` was changed by hand over D-Bus to `Name=Fizz`, `AccessPointName=mobile.bm`, `Protocol=dual`. ofono saves this per IMSI, so it survives a reboot, but a new SIM or a reflashed userdata needs it set again. `media.ng` was not what caused the 4100; it is simply the wrong APN for Fizz.

Measured result (capture in `out/halium14/logs/mobile-data-ok/`, gitignored): in the whole boot, `setupDataCall_1_5` was sent once and succeeded (`status=0, cid=0, ifname=rmnet_data1`). NetworkManager had 0 `Activation: failed`. `rmnet_data1` is `10.116.33.97/30` with a default route through `10.116.33.98`. `ping 1.1.1.1` had 0% loss, 44 to 72 ms. DNS through NM's dnsmasq works. `https://ubuntu.com` returned 200 in 0.87 seconds. Registration was `registered`, `nr`, 302/490 "Fizz" (not roaming). #### MMS sending: what broke it

Symptom: texts send, but every picture ends in "Failed!", and Retry fails the same way. nuntium's log, once per attempt (each Retry is one more):

```
Starting upload of …m-send.req to http://media.videotron.com with proxy :0
m-send.conf ResponseStatus for … is 0
```

That is Vidéotron's MMSC, with no proxy, reached over the default route. It answers with a reply that is not a valid `m-send.conf` (status 0), so nuntium marks the message `PermanentError`.

The cause is leftover state in ofono:

- `/ril_0/context1` (the internet context) still had `MessageCenter=http://media.videotron.com` from the first, wrong apndb provisioning (Vidéotron's `media.ng` is `type=default,mms`). When context1 was changed to Fizz by hand, only `Name`, `AccessPointName` and `Protocol` were changed.
- nuntium (`ofono/modem.go` `GetMMSContexts`) counts an active internet context with a `MessageCenter` as MMS-capable. If that context has ofono's `Preferred=true`, nuntium uses only that context. context1 now has `Preferred=true`, so `/ril_0/context2` ("Fizz MMS", the right MMSC and proxy) was never tried. When MMS worked, context2 was used, so `Preferred` was probably set on context1 later. Most likely the APN page in System Settings set it; this was not confirmed.
- Even with the right MMSC, sending through context1 could not work: nuntium takes the proxy from the context's `Settings.Proxy`, and ofono fills that in only for an `mms`-type context.

Second problem, found after the first fix: context2 has the same APN as context1, so ofono-binder gives both contexts the same data call (`rmnet_data1`). When nuntium deactivates context2 after an MMS (it deactivates every context that is not of type internet), ofono tears down that shared call, and context1 (mobile data) goes down with it: `Deactivating context` / `Clearing active context` twice / `Deactivated data call`. NetworkManager kept showing `ril_0` as connected, but there was no rmnet route left. This is the failure UBports ofono-sailfish #8 describes.

Fix, part 1 (on the phone, saved by ofono per IMSI). This is Fizz's own model, a single `mobile.bm` context with `type=default,mms`:

- context1: `MessageCenter=http://mms.mobile.bm`, `MessageProxy=mmsproxy.mobile.bm:80` (changed while it was inactive). ofono also gives an internet context `Settings.Proxy` (checked), and nuntium never deactivates an internet context. With `Preferred=true`, nuntium uses context1 alone.
- context2 has been removed (`ConnectionManager.RemoveContext`). ofono creates no context like it for a fresh Fizz SIM: `/usr/share/stone/apns-conf.xml` has no Fizz `mms`-only entry. The old context2 came from Vidéotron's provisioning, and was later changed by hand.
- `~/.cache/nuntium/preferredContext` points at `/ril_0/context2`, which is now stale. That does no harm: context1's `Preferred` decides.
- To get NetworkManager back in sync after the shared call was torn down, context1 had to be cycled through ofono (Active false, then true). NetworkManager then restored `default via 10.118.17.105 dev rmnet_data1 metric 700`. `nmcli` cannot control networking from an adb shell (polkit).

User test with Wi-Fi off: a picture was sent (nuntium: `ResponseStatus 128`, `Sent`). That was still through context2, before part 1. The tests after both parts are below.

Fix, part 2 (in the image), for sending with Wi-Fi connected. That send failed at once (`Cannot upload m-send.req …`). With Wi-Fi up:

- `mmsproxy.mobile.bm` and `mms.mobile.bm` only resolve through the carrier DNS (`10.208.36.186`, `10.208.37.47`). NetworkManager's dnsmasq asks the Wi-Fi DNS instead, and gets NXDOMAIN.
- The default route goes through `wlan0`.
- ofono adds no host route for a proxy given as a hostname.

`stone-mms-route.service` (`usr/lib/stone/mms-route.py`, root) watches ofono. For every active context with a `MessageCenter` (or of type mms) it adds `/32` routes through the context's interface and gateway: first for the context's DNS servers, then for the proxy and MMSC addresses, which it resolves by asking those servers directly (a small UDP A-record client). It writes `address name` lines to `/run/stone-mms/mms-hosts`. `etc/NetworkManager/dnsmasq.d/20-stone-mms.conf` (`hostsdir=/run/stone-mms`) makes NetworkManager's dnsmasq serve those names. dnsmasq re-reads a hostsdir by itself when its files change. `usr/lib/tmpfiles.d/stone-mms.conf` creates the directory before dnsmasq starts. The service re-checks on every ofono context signal and every 10 minutes. If a lookup fails, it keeps the last addresses. When it stops, it removes its routes. Live install without a flash: `tools/phone-debug/stone-mms-route-install.sh` (sudo).

Result (live install, Wi-Fi up, 2026-11-10). The service logged routes over `rmnet_data1` (via `10.118.17.105`) for `10.208.36.186` and `10.208.37.47` (DNS) and for `10.208.106.64` and `10.208.106.65`. Both `mms.mobile.bm` and `mmsproxy.mobile.bm` resolve to those two addresses, and they are in `/run/stone-mms/mms-hosts`. The user confirmed all three tests:

1. With Wi-Fi on, a picture was sent (`Starting upload … to http://mms.mobile.bm with proxy mmsproxy.mobile.bm:80`, `ResponseStatus 128`, `Sent`).
2. With Wi-Fi off, a picture was sent, and mobile data still worked afterwards.
3. With Wi-Fi on, a picture was received: `Starting download of http://mms.ingv.ca/… with proxy mmsproxy.mobile.bm:80`, then `m-notifyresp.ind` uploaded.

Limits:

- If an MMS context is separate and only comes up for the MMS (not the case for Fizz now), nuntium could start the upload before the service has added the routes (about 1 s after the context signal). The fix relies on context1 always being up.
- The hosts file keeps the last addresses for 10 minutes. If the carrier changes them, MMS over Wi-Fi fails until the next refresh.
- The carrier DNS addresses get `/32` routes over rmnet. A Wi-Fi LAN that uses those same addresses could no longer reach them.

#### Call audio: what fixed it

> Superseded in part by item 6 ("Call audio routing: what fixed it"): steps 1 to 3 below are now the UCM profile `/usr/share/stone/ucm2/stone/HiFi.conf` applied by PulseAudio, `call-audio-watch.sh` and `~/.config/stone/call-route` are replaced by `call-audio-router.py`, and the route is chosen in the dialer. Steps 4 and 5 and the gain measurements below still hold.

The Android audio HAL cannot be used here (PulseAudio can only load the 64-bit stub `audio.primary.default.so`, item 3), so nothing starts the ADSP voice session. `stone-call-audio.service` (a user unit, enabled through `pulseaudio.service.wants`) runs `usr/lib/stone/call-audio-watch.sh`. It polls ofono's `VoiceCallManager.GetCalls` every 0.5 seconds and, while a call is `dialing`/`alerting`/`active`/`held`, runs `call-audio.sh on`:

1. Mixer, following `mixer_paths_qrdsku1.xml`: earpiece `handset` + `RX_CDC_DMA_RX_0_Voice Mixer VoiceMMode1`. With `~/.config/stone/call-route` set to `speaker`, it uses the existing `speaker-route.sh` chain + `RX_CDC_DMA_RX_1_Voice Mixer VoiceMMode1`.
2. Microphone: by default a single mic, mono (`amic1`, SWR_MIC0/ADC1 -> DEC0; the speaker route uses `amic3`, SWR_MIC4), `TX_CDC_DMA_TX_3 Channels=One`, `VoiceMMode1_Tx Mixer TX_CDC_DMA_TX_3_MMode1`. Without ACDB the voice uses `VSS_IVOCPROC_TOPOLOGY_ID_NONE`. With the two channels of the vendor's `handset-mic` the far end could hear nothing at all.
3. Uplink gain: `TX_DEC0`/`1`/`2 Volume` is set to 84+20 (1 dB/step, 84 = 0 dB) and set back to 84 when the call ends. ACDB normally supplies this gain. Without it, the far end heard speech "drop several times a second" (the vocoder's VAD/DTX dropped the quieter speech). It can be tuned in dB through `~/.config/stone/call-mic-gain` (0 to 40). The in-call recordings through `VOC_REC_UL`, 8 kHz mono, 10 ms windows:

   | Gain | Peak | Clipping | Active speech | Far end |
   | --- | --- | --- | --- | --- |
   | +0 dB | -23.7 dBFS | 0 | -44.8 dBFS | choppy |
   | +14 dB | -14.3 dBFS | 0 | -32.3 dBFS | good once, choppy once |
   | +20 dB (default) | -10.3 dBFS | 0 | -31.1 dBFS | clear |

   "Active speech" is the RMS of the windows more than 4 times above the noise floor (p10). The +20 call also had no PulseAudio crash (the droid card was removed), so the two changes cannot be fully separated. +20 still leaves about 10 dB of headroom.
4. `voice-pcm-hold.py` opens VoiceMMode1 (`hw:0,2`) in both directions, sets parameters, `snd_pcm_start`, and **never reads or writes**. This front end is hostless (`msm-pcm-voice-v2` has no `.copy`/`.pointer` and no DMA buffer). When aplay wrote to it, ALSA copied into a NULL `dma_area`, the kernel oopsed, and `panic_on_oops=1` reset the phone immediately (this happened twice). Once both directions are prepared, the kernel calls `voc_start_voice_call()` for the VoiceMMode1 session (vsid 0x11C05000, which qcril also reports for 3G calls).
5. `ctl-write.py` writes `{0, 0xFFFFFFFF, 20}` to `Voice Tx Mute`, `Voice Tx Device Mute`, and `Voice Rx Device Mute` (the equivalent of the HAL's `voice_set_mic_mute()`). These are write-only array controls that `amixer cset` cannot write.

When the call ends, `call-audio.sh off` stops the holder and clears the mixer and gain. The kernel logs `voice_get_cal: No cal data`, `ADSP_EBADPARAM` (dev cfg), and `voice volume failed` on every call. These are normal without ACDB and do not affect sound.

Known limitations:

- No ACDB calibration: no echo cancellation or noise suppression (fluence/ECNS) and no dual-mic processing. Over the earpiece the far end said it sounded fine. With speakerphone the far end may hear an echo.
- ~~The speaker button in the Phone app does not switch the route.~~ Fixed in item 6 (earpiece, speaker and Bluetooth from the dialer). Wired 3.5 mm headsets: see item 6, "Wired headsets".
- Downlink volume is fixed: the call volume keys change the media volume, not `Voice Rx Gain` (open, see item 6).
- The fallback, if calibration is ever required: the vendor audio HAL is running in the container as `android.hardware.audio@7.0::IDevicesFactory/default` and could be driven over HIDL (`setMode(IN_CALL)` and so on), with ACDB. `module-droid-hidl` is only the AudioSystem passthrough and cannot serve as that client.

### Call audio routing: what fixed it

Ubuntu Touch lets the dialer choose the call output (phone, speaker, Bluetooth). `lomiri-telephony-service-handler` does it by switching the ports of a PulseAudio sink and source; normally the droid card provides them. Here the droid card cannot work (32-bit vendor HAL), so:

1. **UCM profile** `/usr/share/stone/ucm2/stone/HiFi.conf`, verb `Voice Call` (was `HiFi`, renamed for the wired headset, see below) (`ALSA_CONFIG_UCM2=/usr/share/stone/ucm2` for PulseAudio and `stone-call-audio`; only card id `holiqrdsku1sndc` matches). Transcribed from the vendor `mixer_paths_qrdsku1.xml`. The verb sets up the speaker chain and one mic, which PulseAudio's probe needs (MultiMedia5 does not prepare without `RX_MACRO RX2 MUX=AIF2_PB`, MultiMedia1 capture not without a decimator on `TX_AIF1_CAP`). Output devices `Speaker`, `Earpiece`, `Headphones`, `Bluetooth` each carry media, the VoiceMMode1 downlink, the uplink mic chain and the +20 dB uplink gain (Bluetooth: `SLIMBUS_7` at 8 kHz). Input devices `Mic`, `Headset`, `BluetoothMic` route the MultiMedia1 capture front end (`Headset` also moves the call uplink to the headset mic).
2. **PulseAudio** (`etc/pulse/stone-touch.pa`) loads `module-alsa-card use_ucm=1` as `sink.primary` / `source.primary` with ports `[Out] Speaker|Earpiece|Bluetooth` and `[In] Mic|BluetoothMic`. Playback goes through `stone_mm5` (`etc/alsa/conf.d/50-stone.conf`, an alsa-lib `hooks` pass-through around `hw:0,9`): PulseAudio does not rewind a non-hw PCM, which this DSP needs (item 3); `max rewind 0`, 4x10 ms. `71-stone-pulseaudio.rules` keeps udev-detect off the card.
3. **telephony-service** only knows the droid port names. `tools/patch-telephony-ports.py` rewrites seven name constants in place (`output-earpiece` -> `[Out] Earpiece`, ... `input-bluetooth_sco_headset` -> `[In] BluetoothMic`, `output-wired_headphone` -> `[Out] Headphones`, `input-wired_headset` -> `[In] Headset`) into `/usr/bin/lomiri-telephony-service-handler-stone`. It has to be in `/usr/bin`: elsewhere the handler thinks it is uninstalled, cannot find its protocol files, and never handles a call. `/usr/lib/stone/telephony-service-handler.sh` starts it only while the stock binary is the exact build it was patched from (SHA256 `f369e392…`), otherwise the stock handler.
4. **`call-audio-router.py`** (`stone-call-audio.service`, event driven: ofono signals and `pactl subscribe`) does what the HAL would do on top of the routing: runs the voice session while ofono has a call (`call-audio.sh on`: `voice-pcm-hold.py` + unmute), restarts it when the port changes, mirrors the source mute (dialer's mute button) into `Voice Tx Mute`, and keeps `source.fake.sco` open while the port is Bluetooth. That makes UT's bluez module ("SCO over PCM") open the SCO link, and the BT chip only appears on SLIMbus while the link is up, so the link must exist before the voice session starts (the router waits 0.6 s for the port to settle). If `sink.primary` is missing 10 s after PulseAudio starts, the router falls back to a plain `sink.speaker` (no call routes) so there is always a speaker.

Uplink levels measured with `call-audio.sh rec-ul` (`VOC_REC_UL`, 8 kHz): built-in mic at +20 dB peaks at -10 dBFS (item 5); the earbuds' mic (Moondrop Nekocake, CVSD) peaks at -6 dBFS with speech at about -20 dBFS RMS, so it needs no extra gain.

### Wired headsets (3.5 mm and USB)

Status: fixed and confirmed by the user on 2026-11-10 (image `f054cb90…`, kernel `#11`, patches 0003 and 0004). 3.5 mm: media switches on plug/unplug, calls use the headphones and a 4-pole headset's mic. USB: media and calls, with the headset mic, plugged in at boot or during a call.

#### 3.5 mm: what was missing

- Detection works in the kernel. The codec is a WCD937x; its headset detection (MBHC, `wcd-mbhc-v2.c`) logged `Headphone plug in`, and the input device `holi-qrdsku1-snd-card Headset Jack` had `SW_HEADPHONE_INSERT` and `SW_JACKPHYSICAL_INSERT` set (the user's earphones read as 3-pole: no mic bit, impedance 70/49 Ω).
- PulseAudio cannot use input events. It only follows ALSA jack controls (UCM `JackControl`), and the card has none: `snd_soc_card_jack_new()` is called without pins, so the jack is only an input device.
- Adding jack controls to the main card would not help. PulseAudio reads them through alsa-lib's mixer (`prepare_mixer()`: `snd_mixer_selem_register` + `snd_mixer_load`), and that already fails on this card (`Unable to load mixer: No such device`). The simple mixer reads every boolean/integer/enum control while loading (`simple_add1()` -> `selem_read()`), and 151 vendor controls fail to read: 80 `EINVAL` (`ADSP Stream Callback Event N`, `Sound Focus ...`, `Source Tracking ...`), 50 `EPERM` (write-only, such as `Voice Rx Gain`, `Voice Tx Mute`, `Playback ION FD N`), 16 `ENODEV` (`Capture/Playback N Soft Vol Params`, `Capture 4 Volume`), 4 TLV `ENXIO`, 1 `EAGAIN`. alsa-lib's `remap` ctl plugin cannot hide controls.
- No route: there were no UCM devices for headphones or the headset mic, and telephony-service did not know their port names.
- The vendor HAL also sets `RX HPH Mode` to `CLS_H_ULP` at boot; here it was still `CLS_H_INVALID`.

#### 3.5 mm: the fix

1. **Kernel** (`kernel/patches/0003-wcd-mbhc-jack-controls-on-own-card.patch`, kernel `#10`): at MBHC init, `wcd-mbhc-v2.c` registers a second ALSA card, id `StoneJack` (card 1; the main card already holds 0 at that point). Its only controls are `Headphone Jack` (headphone or line-out bit) and `Headset Mic Jack`, on a phantom jack (no second input device). `wcd_mbhc_jack_report()`, which every headset report goes through, mirrors the jack status into it. alsa-lib's mixer loads that card without trouble.
2. **UCM** (`HiFi.conf`): output device `Headphones` (vendor `headphones` + `low-latency-playback headphones` + `voicemmode1-call headphones`: RX_CDC_DMA_RX_0 stereo to HPHL/HPHR with the compander, class-H ULP mode, the voice downlink, uplink from the main mic at +20 dB), `PlaybackPriority 400`, `JackCTL "hw:StoneJack"`, `JackControl "Headphone Jack"`. Input device `Headset` (vendor `headset-mic`/`amic2`: ADC2 input `INP2` through the same DEC0 -> TX_CDC_DMA_TX_3, so it serves both recording and the call uplink), `CapturePriority 200`, `JackControl "Headset Mic Jack"`; disabling it goes back to the main mic. `module-switch-on-port-available` (already loaded) moves media to the headphones on plug-in and back on unplug.
3. **Verb renamed** from `HiFi` to `Voice Call` (`stone.conf`). telephony-service only follows a plug or unplug during a call (`updateCardCallback`) on the card whose profile is called `voicecall` or `Voice Call`. It is still the only verb; PulseAudio only uses the name for the verb priority.
4. **telephony-service**: two more names patched, `output-wired_headphone` -> `[Out] Headphones` and `input-wired_headset` -> `[In] Headset` (both referenced only at their start; new output SHA256 `ec663f6d…`). The handler offers "wired" while that port is not marked unavailable, uses it by default for calls (`AudioModeBtOrWiredOrEarpiece`), and takes its mic only when `[In] Headset` is available, so a 3-pole plug uses the phone's mic.
5. `71-stone-pulseaudio.rules` keeps module-udev-detect off `StoneJack` (no PCMs).
6. **Guard in the router**: without the jack card, PulseAudio would mark `[Out] Headphones` "availability unknown"; being the highest priority, it would be picked at startup (silent speaker), and telephony-service would put every call on it. If the router sees that, it logs an error and moves off that port (to the earpiece in a call, the speaker otherwise).

Checked on the phone before building (old kernel, so no jack card yet): the profile parses with `alsaucm` (verb `Voice Call`, devices Speaker, Earpiece, Headphones, Bluetooth, Mic, Headset, BluetoothMic; `JackCTL`/`JackControl` read back). Enabling `Headphones` under a running PulseAudio stream ran every control write (`RX HPH Mode` = `CLS_H_ULP`, `RX_CDC_DMA_RX_0 Channels` = Two, RDAC on) and started the RX_0 back end without kernel errors; afterwards the speaker route was restored through PulseAudio. Not listened to yet.

#### USB headsets in calls

telephony-service already handles USB (`output-usb_headset`, `output-usb_device`, `input-usb_headset`), but only as ports of the same sink as the earpiece, and only when PulseAudio marks them available (`PA_PORT_AVAILABLE_YES`, stricter than for the 3.5 mm ports). A USB headset here is a separate PulseAudio card on the host `snd-usb-audio` driver, which the handler never looks at, so the dialer offered only earpiece and speaker.

The fix follows Android: the DSP plays the call on its `USB_AUDIO_RX` back end and the kernel's USB audio offload service (`CONFIG_SND_USB_AUDIO_QMI=y`, `usb_audio_qmi_svc.c`) gives it the device's endpoint.

1. **UCM** device `USB` (port `[Out] USB`): `USB_AUDIO_RX Audio Mixer MultiMedia5`, `USB_AUDIO_RX_Voice Mixer VoiceMMode1`, uplink from the main mic at +20 dB. `PlaybackPriority 10`, so PulseAudio never moves `sink.primary` there by itself (media keeps using PulseAudio's own USB sink). `JackCTL "hw:StoneJack"`, `JackControl "USB Jack"`.
2. **`/usr/lib/stone/usb-audio-jack.py`**, run by udev (`72-stone-usb-audio.rules`) when the control device (`controlC*`) of the built-in card, of StoneJack or of a USB card appears, and when a sound card goes. At boot a USB headset appears at about 3 s and StoneJack in the middle of the built-in card's setup, before the built-in controls exist; whichever run comes last finds everything (a card's own `add` event comes before its control node, so the card events were not enough). It creates `USB Jack` on the StoneJack card if missing: a user-space boolean on the CARD interface, which survives the process and which phablet (group audio) could also write. It picks the first USB card with a playback stream from `/proc/asound/cardN/stream*`, chooses a format the device has (S16_LE at 48 kHz first), writes `USB_AUDIO_RX dev_token` = `card << 16 | device << 8 | 0` plus `Format`/`SampleRate`/`Channels`, and sets `USB Jack`. The token has to be written raw: the control's range reads as 0..-1 (UINT_MAX), and `amixer` (and UCM `cset`) clamp any value to 0xffffffff. The first test did exactly that: `handle_uaudio_stream_req: invalid card # 255`, `AFE enable for port 0x7000 failed -131`.
3. **telephony-service**: `output-usb_device` -> `[Out] USB` (referenced only at its start; output SHA256 `ae0b0a94…`). The handler treats it like wired headphones, so the uplink stays on the phone's mic.
4. **Router**: while `sink.primary` is on `[Out] USB` (call or not: PulseAudio applies the route the moment telephony-service selects it), it suspends PulseAudio's `alsa_output.usb-*` sinks and `alsa_input.usb-*` sources (`pactl suspend-sink/-source … 1`) so the host driver has the streams closed for the DSP (the sink may still be open from the ringtone), and resumes them afterwards. Outside calls it moves `sink.primary` off `[Out] USB` (to the 3.5 mm headphones if plugged, else the speaker) and `source.primary` off `[In] USBMic`: telephony-service selects "wired" at startup and when a call ends, and outside calls the device's media goes through PulseAudio's own USB sink.
5. **USB mic** (`USBMic` device, port `[In] USBMic`): `VoiceMMode1_Tx Mixer USB_AUDIO_TX_MMode1` replaces the main mic in the uplink, `MultiMedia1 Mixer USB_AUDIO_TX` for recording; `CapturePriority 10`, `JackControl "USB Mic Jack"`. `usb-audio-jack.py` also writes `USB_AUDIO_TX dev_token` (direction 1), format, rate and channels, and sets `USB Mic Jack`, only when the card that plays also has a capture stream. telephony-service: `input-usb_headset` -> `[In] USBMic` (output SHA256 `bdecab37…`); the handler takes it as the call mic whenever it is available.
6. **Defaults**: `stone-touch.pa` sets `sink.primary`/`source.primary` as defaults after module-udev-detect has already added a USB card present at boot, and module-switch-on-connect does nothing during startup; and at hang-up telephony-service restores the defaults saved at call start (the built-in ones if the headset was plugged in during the call). The router makes PulseAudio's USB sink and source the defaults when it first sees PulseAudio with a USB card present, and for 15 s after a call (`prefer_usb_defaults()`).
7. **Kernel** (`kernel/patches/0004-usb-audio-qmi-do-not-take-host-open-streams.patch`): the offload service refuses an enable while the host driver has the PCM open (`subs->pcm_substream`, `-EBUSY`; the DSP retries), and a disable only touches the hardware when the offload owns the interface. ### Call audio route selection (investigation log)

How Ubuntu Touch does it: `lomiri-telephony-service-handler` (`handler/qpulseaudioengine.cpp`) looks for a PulseAudio sink that has both an `output-earpiece` and an `output-speaker` port (plus `output-bluetooth_sco` when a bluez card offers HFP/HSP). At call start it switches the bluez card to HFP, then sets the sink/source ports; at the end it restores A2DP and the speaker port. Normally the droid card provides those ports. Here there is no such sink, so the dialer gets no choices and the speaker button did nothing (a limitation noted in item 5).

### Camera: what fixed it

1. **Kernel, shared VIO pin** (`kernel/patches/0005-cam-sensor-continue-power-up-on-shared-gpio.patch`, kernel `#12`): all sensors and the flash use TLMM pin 38 as their VIO enable, which the DT does not list as shared. A second camera device's power-up got `-EBUSY` on that GPIO and was aborted, and CamX aborted in `CSLAcquireDevice`. Now `-EBUSY` from the table request is logged and power-up continues, like Xiaomi's prebuilt `camera.ko` does; `custom_gpio1_powernum` keeps the pin up until the last user powers down.
2. **No logical multi-sensor cameras**: CamX's `camxoverridesettings.txt` gets `MultiCameraEnable=FALSE`, and `persist.vendor.camera.mapid=0` turns off Xiaomi's camera role-ID remapping. Otherwise camera 0 is a logical wide + depth camera: with the remapping (default) the real-time bokeh pipeline, whose Xiaomi AlgoControl node hits a compiler-inserted bounds trap and aborts the provider; without it, a wide + depth session whose preview shows the monochrome depth sensor (grey picture in a green frame). Both are vendor files: `boot/ut-init/stone-vendor-fixups.py` (runs at every boot from the initramfs, reads `vendor_b`) writes an edited `camxoverridesettings.txt` (pinned to SHA256 `ee6e420d…`, only that line changed) and a `build.prop` with the property appended into `/usr/share/halium-overlay/android/vendor/`, which `mount-halium-overlay` bind-mounts over the originals before the container starts. A value persisted in `/data/property` wins over the `build.prop` default; on the test phone it is already `0`.
3. **Video recording release** (`tools/patch-libaudioclient.py`): `AudioSystem::releaseAudioSessionId()` in the Halium `libaudioclient.so` waited forever for an AudioFlinger this system does not have, so every recorder release hung camera_service and the app. It now returns at once. `build-boot-image.sh` extracts the library from `android-rootfs.img` (SHA256 `97144b4e…` in, `5fe2f500…` out) and ships it as `/usr/share/halium-overlay/android/system/lib64/libaudioclient.so`.

### Implementation notes

- `/data/tombstones` is world-readable here (no root needed), and a tombstone carries the process's recent logcat, so it is the best source while `logcat` needs root.
- The crash (`tombstone_44`): `camera.qcom.so` (CamX) aborts in `CSLAcquireDeviceHW` with "AcquireDevice failure … deviceIndex: 16, Name=CSLHwImageSensor, result=1". The session is a multi-camera one: CamX maps the app's camera "0" to logical camera 3 (`configure_streams() … logicalCameraId: 3, cameraId: 0`, `BokehMode Value 1`, `numActiveCameras = 2`), i.e. wide + depth together (`camxoverridesettings.txt`: `MultiCameraEnable=TRUE`, `isPhyicalMultiCameraSupported=TRUE`).
- Kernel side of the same moment: the main sensor powered up (`CAM_ACQUIRE_DEV Success, sensor_id:0x4842`), the depth sensor's power-up failed: `cam_res_mgr_gpio_request: gpio 393:CAM_VIO2 request fails rc = -16`, then `cam_sensor_core_power_up: request gpio failed` and `Sensor Power up failed`.
- Why: every camera sensor and the flash use TLMM pin 38 (GPIO 393: TLMM is `gpiochip0`, base 355) as their VIO enable, as `gpio-custom1` (`CAM_VIO0/1/2/CAM_VIO`, the flash's `CUSTOM_GPIO1`). The DT's `qcom,cam-res-mgr` lists only `gpios-shared = <407>`, which is copied from the Qualcomm reference board (`blair-camera-sensor-qrd.dtsi`, its flash enable pin) and is pin 52 here, unused. So the second sensor's `gpio_request` gets `-EBUSY`, `no_gpio` is set, and `cam_sensor_core_power_up()` aborts at the first reset step. Only a `CUSTOM_GPIO1` step was allowed to continue.
- Stock does not stumble on this because Xiaomi's prebuilt `/vendor/lib/modules/camera.ko` continues power-up after a failed gpio request: its strings have `request gpio failed,still do power up` and no aborting variant, next to the same `custom_gpio1_powernum` reference count that this tree has. Xiaomi's own kernel tree (`android_kernel_xiaomi_stone`) has the same aborting code as ours.
- Fix (`kernel/patches/0005-cam-sensor-continue-power-up-on-shared-gpio.patch`, kernel `#12`): when the gpio table request fails with `-EBUSY` (another camera device holds a shared pin), log it and continue the power-up; any other gpio error still aborts. The shared pin is already driven by its holder, and `custom_gpio1_powernum` keeps it up until the last user powers down. Putting pin 38 into `cam_res_mgr`'s shared list instead was rejected: its own on/off counting would double up with `custom_gpio1_powernum` and could leave VIO on after the camera is closed.
- Seen on the way, not camera (the HAL does exist, see the correction above): init asks for an Android sensors HAL (`android.hardware.sensors@2.1/2.0/1.0`) once a second and finds none, and the camera app logs "There is no sensor manager yet" (no orientation sensor; proximity during calls likely affected too). `vndservicemanager` and `mediaextractor` abort on every boot (tombstones 00 to 49).

What has to be done before `apt full-upgrade` is safe:

1. The image ships copies of two programs, patched from the exact versions in `out/halium14/rootfs-tree`:
   - `/usr/lib/stone/media-hub-server` (package `media-hub`, `tools/patch-media-hub.py`);
   - `/usr/bin/lomiri-telephony-service-handler-stone` (package `lomiri-telephony-service`, `tools/patch-telephony-ports.py`).

   After an upgrade of those packages, the copies would be stale: they could break against the new libraries, and they would miss the upstream fixes.
   - Stop-gap: `sudo apt-mark hold media-hub lomiri-telephony-service`.
   - Real fix: patch at boot from whatever binary is installed, the way `stone-vendor-fixups.py` works for the vendor files. Both patch scripts check SHA256 hashes, so an unknown version is left unpatched (and reported) instead of patched blindly. A new upstream version then needs its offsets updated in the patch script.
2. Packages this port's fixes depend on. After an upgrade of these, check calls, data and MMS again:
   - `ofono-sailfish`: context handling, `Settings.Proxy` on internet contexts, `InUse` on active contexts.
   - `nuntium`: the MMS context selection in `GetMMSContexts`.
   - `sensorfw-qt5` and `libsensorfw-qt5-hidl`: the AIDL path.
   - `libgbinder`: presets.
   - `pulseaudio`: the UCM card.
3. `lineageos-apndb`: `build-boot-image.sh` builds `/usr/share/stone/apns-conf.xml` from the copy in `rootfs-tree`. A newer apndb on the phone does not reach that copy until the image is rebuilt from an updated tree.
4. Then: `sudo apt update && sudo apt full-upgrade` on the phone. Rebuilding the rootfs from a newer CI tarball is the wrong way: it means reinstalling the rootfs.
